## 第 1 章 这游戏是用什么做的（技术栈大白话）

你不需要会这些技术，但要知道**每个东西负责什么**，以后听我说才不会懵。

| 名字 | 它是干什么的 | 打个比方 |
|------|--------------|----------|
| **Phaser** | 游戏引擎。负责把图画到屏幕上、播放动画、接受你的点击和触摸 | **剧院**：舞台、灯光、幕布、演员调度 |
| **TypeScript** | 写游戏规则的语言。比普通 JavaScript 多一层"格式检查" | **剧本**，而且是有格式要求的剧本，写错格式会当场被指出来 |
| **Vite** | 构建工具。把散落的代码文件整理成一个浏览器能跑的东西 | **剧场管理员**：把剧本、道具、布景归置好，开演时快速搭台 |
| **Node.js** | 让电脑能直接运行程序的环境（不用打开浏览器） | **后台工作人员**：负责跑测试、生成预览图这些幕后活 |
| **Electron** | 把网页游戏打包成电脑上能双击运行的软件 | **把舞台搬进一个专门的剧场**（Steam 上架用这个） |
| **Capacitor** | 把网页游戏打包成手机 App | **把舞台装进一辆巡回演出车**（手机应用商店用这个） |

### 一个关键理解

**你的游戏本质上是一个网页**。"电脑版"和"手机版"都是把这个网页装进一个外壳里。所以三种平台共用同一套代码——这就是为什么技术选型里没有"分别开发三次"。

### 一条重要分界线：`core` 和别的东西

| | `src/core/` | 其他所有地方 |
|---|---|---|
| 能不能碰画面 | **绝对不能** | 可以 |
| 能不能单独测试 | **能**，不需要浏览器 | 一般要浏览器 |
| 改动风险 | **高**，很多功能依赖它 | 相对低 |

**为什么这么分？** 因为"算伤害"和"画伤害数字"是两件事。分开以后：① 战斗结果能脱离画面单独验证，不会因为画面卡顿导致数值算错；② 将来换画面风格，数值逻辑一行都不用动。

这是你项目里的**第 1 条架构铁律**：`core` 层禁止引入 Phaser。测试会守住这条线。

## 第 3 章 游戏是怎么"动起来"的（最重要的一章）

### 打个比方：皮影戏

传统做法是**画动画**：一个挥刀动作画 12 张图，翻页一样播出来。问题是——你有 87 门功法、12 个角色，全画一遍是 **1044 套动画**，画到下辈子。

你的项目用的是**皮影戏做法**：

| 皮影戏 | 你的项目 |
|--------|----------|
| 一个皮影人由 17 块皮子组成 | 角色的 17 个部件（`slot`） |
| 每块皮子用关节钉住 | 骨骼的父子关系 |
| 耍皮影的人扳动关节 | 动作数据里的角度 |
| **换一个皮影人，动作照样能耍** | **换一个角色，动作数据照样能用** |

这就是为什么只需要 **9 个动作** 就能覆盖 87 门功法——因为动作是"耍法"，不是"皮子"。

### 五步流水线（看懂这五步，你就看懂了整个项目）

| 第几步 | 是谁做的 | 输入 | 输出 | 大白话 |
|:------:|----------|------|------|--------|
| 1 | 骨架定义 `src/data/rigs.ts` | 手写的骨长数据 | 一副骨架（17 个部件的位置和大小） | **皮影人长什么样** |
| 2 | 动作数据 `src/data/motions/*.json` | 手写的角度数据 | 一条时间轴 | **每个时刻关节扳到几度** |
| 3 | 采样器 `src/core/anim/clip.ts` | 时间（比如 156 毫秒） | 这一刻所有关节的角度 | **"倒带"到第 156 毫秒，这一刻啥姿势** |
| 4 | 求解器 `src/core/anim/skeleton.ts` | 关节的相对角度 | 每个部件在屏幕上的绝对位置 | **一层层加上去，算出每块皮子在哪** |
| 5 | 渲染（现在的预览 / 将来的 Phaser） | 绝对位置 | 屏幕上的图像 | **照着位置把皮子画出来** |

**第 3、4 步为什么要分开？**
因为手相对胳膊、胳膊相对身体、身体相对地面——你扳的是"相对角度"，但画的时候需要"屏幕上的绝对位置"。第 4 步就是做这个换算的。这跟人的身体是一个道理：你说"抬起前臂"，其实是肘关节和手腕一起动了。

### 用真实数据走一遍：0.52 秒的挥刀

打开 `src/data/motions/dao_atk_a.json`，这是一个 520 毫秒的挥刀动作。它的时间轴（`t` 是进度，0 = 开始，1 = 结束）：

| 进度 | 换算成时间 | 右上臂角度 | 躯干角度 | 同时发生了什么 |
|:----:|:----------:|:----------:|:--------:|----------------|
| 0 | 0 ms | +0.05 | 0 | 站姿起始 |
| 0.06 | 31 ms | — | — | 触发音效"轻挥" |
| 0.30 | 156 ms | **−2.05** | −0.16 | **举刀到最高点** |
| 0.32 | 166 ms | — | — | 触发特效"弧形斩击" |
| 0.45 | 234 ms | — | — | **命中判定时刻** |
| 0.50 | 260 ms | −0.62 | +0.26 | 刀劈下来，身体前压 |
| 0.55 | 286 ms | — | — | 触发屏幕震动（轻） |
| 0.85 | 442 ms | — | — | 特效停止 |
| 1.00 | 520 ms | +0.05 | 0 | 回到站姿 |

> 顺带解释一个坑：−2.05 是"举刀最高"，看着像负数是"往下"？不是。**在这个坐标系里正角度是顺时针**，也就是往后甩。右向角色要往前上方举刀，必须用大负角度。这条最容易出错，已经写进规范文档了。

**注意"打斗节奏"是怎么来的**：真正决定手感好不好的，是 0.06 出音效、0.32 出特效、0.45 判定命中、0.55 震屏这**四个时间点**的先后配合。这跟电影剪辑是同一个道理。

## 第 4 章 三个核心概念（记住这三个就够用了）

### 4.1 slot（部件名）—— 17 个固定名字

| 中文 | slot 名 | 父级 |
|------|---------|------|
| 腰根 | `pelvis` | —（根） |
| 躯干 | `torso` | pelvis |
| 头 | `head` | torso |
| 右上臂 / 右前臂 / 右手 | `upperArmR` / `forearmR` / `handR` | 依次相连 |
| 武器 | `weapon` | handR |
| 左上臂 / 左前臂 / 左手 | `upperArmL` / `forearmL` / `handL` | 依次相连 |
| 右大腿 / 右小腿 / 右脚 | `thighR` / `shinR` / `footR` | 依次相连 |
| 左大腿 / 左小腿 / 左脚 | `thighL` / `shinL` / `footL` | 依次相连 |
| 披风 | `cloak` | torso（可选） |

**铁律：所有角色共用这一套名字。**

> 为什么这么严？因为动作数据是"按 slot 名"写的。如果某个角色多长出一个部件，这套动作就不适用了，你得给**它单独做一整套动画**——资产量立刻爆炸。所以"新增角色只能换贴图，不能加部件"。

### 4.2 挂点 anchor —— 特效的挂钩

挂点是"贴在某个部件上的一个点"，用来标记**特效该从哪冒出来**。

| 挂点名 | 中文 | 用在哪 |
|--------|------|--------|
| `weaponTip` | 武器尖端 | 刀光、剑气从这出发 |
| `palm` | 掌锋 | 掌风、气劲 |
| `throwPoint` | 掷出点 | 暗器 |
| `bodyCenter` | 身体中心 | 环形气劲、护体光 |
| `footPoint` | 脚底 | 位移残影、落地墨点 |
| `hitPoint` | 命中落点 | 打击特效 |

**关键设计：特效只认挂点，不认动作名。**

意思是——"弧形刀光"这个特效，它只知道"我要从 `weaponTip` 出发"，它**不知道**自己是被哪门功法触发的。所以 87 门功法可以共用同一批特效模板（实际只用了 16 种特效模板）。

如果反过来设计（特效写死"我是断岳刀法的专属特效"），那就是 87 个特效，工作量翻 5 倍。

### 4.3 事件 event —— 时间轴上的"通知"

动作数据里有一串事件，是**给别人看的信号**，自己不参与数值计算：

| 事件类型 | 意思 |
|----------|------|
| `sfx` | 该放音效了 |
| `vfx` | 该出特效了 |
| `hit` | **该判定命中了**（最关键的一个） |
| `vfxStop` | 特效该收了 |
| `shake` | 该震屏了 |

**为什么要用"事件"而不是写死在代码里？**
因为这样一来，"什么时候命中"这件事变成了**数据**。你想让某个动作快一点命中，改 JSON 里 `hit` 那一刻的 `t` 就行，不用改代码。

### 4.4 补充：缓动 ease —— 让动作不像机器人

如果关节角度是匀速变化的，看起来会非常僵硬。所以加了"缓动"（速度曲线）：

| 缓动名 | 感觉 |
|--------|------|
| `linear` | 匀速，机械感 |
| `sineIn` | 慢慢起步 |
| `sineOut` | 慢慢停下（最常用） |
| `quadIn` | 加速冲（适合下劈） |
| `backOut` | 冲过头再弹回来（适合收势） |

**全项目只有这 5 种**，是故意限制的——选择太多反而不统一，手感会乱。

## 第 5 章 为什么这样设计省了多少钱（你该知道的价值）

| 对比项 | 笨办法（每个功法单独做动画） | 你的项目（共用动作 + 换特效） |

### 实操 1：改角色配色（最简单的）

|----|------|

| 注意 | 颜色必须是 `#` 加 6 位字符，写错了浏览器会变透明 |

### 实操 2：改动作幅度（让刀举得更高）

| 项 | 内容 |
|----|------|
| 改哪个文件 | `jianghu-game/src/data/motions/dao_atk_a.json` |

| 生效条件 | 同上，跑一次生成命令再刷新 |
| ⚠️ 重要警告 | **正数是往后甩（会穿模），负数是往前上方举。** 这是本项目最容易搞错的地方 |

### 实操 3：改某门功法配什么特效

| 项 | 内容 |
|----|------|
| 改哪个文件 | `jianghu-game/src/data/gongfa_visual.ts` |
| 找什么 | 按功法名字搜，比如搜 `断岳刀法`（在第 120 行） |
| 它长什么样 | 它是一个**方括号数组**，每一格的含义是固定的，见下方表格 |
| 怎么改 | 找到第 4 格（特效），把 `'slash_heavy'` 换成别的 |
| 可选值 | `slash_arc`（弧形斩）/ `slash_heavy`（重斩）/ `thrust_multi`（多重刺）/ `palm_burst`（掌爆）/ `aura_ring`（环形气劲）/ `ink_splash`（墨溅）等 16 种 |
| ⚠️ 重要 | **必须数准格子**：一格都不能多、不能少，顺序也不能换，错位了程序会直接报错 |
| 生效条件 | 目前只影响数据校验，画面效果要等战斗场景做出来 |

「断岳刀法」这一行的 10 个格子，从上到下依次是：

| 第几格 | 含义 | 断岳刀法的值 |
|:------:|------|--------------|

| 2 | 显示名 | `'断岳刀法'` |
| 3 | 用哪个动作 | `'atk_b'` |
| 4 | **特效（你要改的就是这格）** | `'slash_heavy'` |
| 5 | 时序倍率（小于 1 更慢更重） | `0.85` |
| 6 | 命中停顿（毫秒） | `90` |
| 7 | 屏幕震动（0 无 / 1 轻 / 2 重） | `2` |
| 8 | 音效 | `'swing_heavy'` |
| 9 | 打击范围 | `'column'`（一列） |
| 10 | 品质 | `'liang'`（良品） |

## 第 7 章 JavaScript 和 TypeScript，你到底该选哪个

### 先说结论

**我推荐继续用 TypeScript（选项 A）**，但理由可能和你想的不一样。

### 用你项目里的真实代码对比

同一段"躯干"的定义，两种写法是这样：

| | 写法 |
|---|---|
| **TypeScript（现在用的）** | 先写一段"规格说明"：躯干这个格子，`slot` 必须是 17 个合法名字之一，`parent` 要么是名字要么是空，`offset` 必须是两个数字……然后才写实际数据 `{ slot: 'torso', parent: 'pelvis', offset: [0, -6] }` |
| **JavaScript** | 直接写 `{ slot: 'torso', parent: 'pelvis', offset: [0, -6] }`，没有那段规格说明 |

### 所以差别到底在哪

| 差别 | 说明 |
|------|------|
| TypeScript 多出的部分 | 大约 30% 的代码是"**给电脑看的规格说明**"，不是游戏逻辑本身。它不产生任何游戏效果 |
| 这 30% 有什么用 | ① 你不小心把 `offset` 写成 `"零下六"`，**保存时就报错**，不用等游戏跑崩；② 编辑器会自动提示你"这里该填什么" |
| 对你（新手）的实际体验 | 多看到一些冒号和英文单词，但**多了护栏**。改坏了立刻知道，而不是玩到第 3 关才发现 |
| 能不能自己看懂逻辑 | **能，两种都能**。真正让你看不懂的是游戏逻辑本身，不是那几个冒号 |

### 我为什么改推荐 A（诚实说明）

我第一条消息里推荐的是"混写"，把差异摊开讲之后我改了，因为：

| # | 理由 |
|:-:|------|
| 1 | **混写会给你两套语法**。这个文件有冒号、那个没有，对新手是加困惑不是减负 |
| 2 | **你真正想要的"自己改"，主要落在 JSON 数据上**（第 6 章那三个实操），跟代码语言无关 |
| 3 | TypeScript 的标注是**护栏**：新手最怕"改坏了我不知道"，它恰好解决这个 |
| 4 | 已有代码与 60 项测试都是 TS，混写会让检查出现漏网之鱼 |

### 你的决定不急

看完这一章，如果你还是觉得"我就想看到清清爽爽的代码"，告诉我，**改成选项 B 只需要我调整新代码的写法，已有的东西一行都不用重写**。

唯一的坑是选项 C（全面退回 JS）：那要重写已有的全部代码和测试，**不推荐**。

## 第 8 章 术语速查表

以后听到这些词，回来查这张表：

| 术语 | 大白话 |
|------|--------|
| **引擎 / Phaser** | 帮你把图画到屏幕上、处理点击和动画的现成工具箱 |
| **TypeScript / TS** | 带格式检查的 JavaScript |
| **Vite** | 把代码文件整理成浏览器能跑的东西的工具 |
| **slot** | 角色身上的一个部件位置，17 个固定名字 |
| **骨骼 / bone** | 皮影人身上的一块皮子 + 它的关节 |
| **骨架 / rig** | 一整套骨骼，决定这个角色长什么样 |
| **体型** | 骨架的尺寸预设，现在有 3 套 |
| **clip / 动作** | 一段有时长的表演，比如"0.52 秒的挥刀" |
| **轨道 / track** | 一个部件的角度随时间的变化 |
| **关键帧 / keyframe** | 时间轴上的一个控制点，比如"第 0.3 处，胳膊转到 −2.05" |
| **缓动 / ease** | 速度曲线，让动作不是匀速的 |
| **挂点 / anchor** | 特效的挂钩位置，如刀尖、掌心 |
| **事件 / event** | 时间轴上的通知，如"现在命中" |
| **局部坐标 / 世界坐标** | 局部 = 相对老爸的位置；世界 = 相对屏幕的位置 |
| **采样 / sample** | 给定一个时间点，算出那一刻的姿势 |
| **JSON** | 一种给电脑和人都能读的数据文件格式，用来存配置和数值 |
| **配置表 / 数据驱动** | 把数值和规则放在文件里，而不是写在代码里 |
| **硬编码** | 把数值直接写死在代码里（本项目**禁止**） |
| **core / 内核** | 只管算、不管画面的那部分代码 |
| **渲染 / render** | 把算好的位置画成图像 |
| **对象池** | 提前造好一堆东西反复用，避免频繁新建造成卡顿 |
| **CDN / 依赖** | 别人写好的现成代码库 |
| **npm / pnpm** | 下载和管理"别人写好的代码库"的工具 |
| **构建 / build** | 把源代码加工成能发布的成品 |
| **打包** | 把网页变成电脑软件或手机 App |
| **测试 / test** | 自动检查代码有没有改坏的脚本 |
| **CI** | 每次改代码都自动跑一遍检查的机器人 |
| **重构** | 不改功能，只把代码整理得更清晰 |
| **类型 / type** | TypeScript 里的"规格说明"，规定一个格子能填什么 |
| **编译 / 转换** | 把 TypeScript 变成浏览器认识的 JavaScript |
