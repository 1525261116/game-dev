## 0. 结论先行

**新增约束**：开发者 = 1 人（个人），开发方式 = **vibe coding（由 AI 写代码，人做决策与验收）**。

这个约束把选型的**第一权重从"引擎能力"换成了"AI 能不能自己把项目跑起来并验证"**。按新的权重重算：

| 技术栈 | 引擎能力视角得分（上一版报告） | **vibe coding 视角得分（本报告）** | 结论变化 |
|--------|:------------------------------:|:----------------------------------:|----------|
| **TypeScript + Phaser 3 + Vite** | ≈ 3.0 / 5 | **4.6 / 5** | ⬆️ **升为首选** |
| Unity 6.x LTS | **4.4 / 5** | 3.2 / 5 | ⬇️ 降为备选 |
| Cocos Creator 3.8 | 3.8 / 5 | 3.3 / 5 | 不变（第二备选） |
| Godot 4.6 | 3.3 / 5 | 3.2 / 5 | 不变 |

**三条核心判断**

1. **Web 栈（Phaser + TS）在 vibe coding 下的决定性优势是"可验证闭环"**：我能把游戏真正跑起来、截图、跑自动化战斗模拟、跑配置表校验——而 Unity/Godot 的场景与编辑器操作我无法执行（无 GUI 权限、需许可证、`.unity`/`.prefab` 是编辑器产物而非纯文本）。**AI 写代码的最大风险是"写了但不知道对不对"，Web 栈能自证，Unity 栈只能靠人肉点验证。**
2. **但引擎选择其实是"美术表现形态"决策的下游**：若坚持**真 2.5D 等距 + 实时 2D 光照 + 自由镜头**，Unity 更稳；若接受**手绘背景 + 斜视角伪 2.5D（无旋转、光照烘焙进贴图）**——这对个人开发现实得多——**Web 栈完全够用，且 Unity 的主要优势随之消失**。
3. **推荐路径：以 Web 栈立项，但设一道 2 周 Gate**。Gate 要验的是三件我无法替你判断的事：① 水墨质感在 Phaser 里能否达标 ② 中低端 Android WebView 能否 30FPS/内存达标 ③ Steam+Electron 出包与 IAP 是否通。**过则继续，不过则切 Unity——而 GDD 的数据契约（24 张表）与全部设计成果都不浪费。**

> ⚠️ **诚实交代**：本会话沙箱内 `npm registry` 不可达（`registry.npmjs.org → 000`），我**无法自行安装依赖**。但已实测：本机 **Chrome 无头模式 + WebGL 2 + 截图读取全部可用**（详见 §8）。因此只要你本地执行过一次 `pnpm install`，后续我就能自己跑构建、跑测试、截图验证——这正是本文结论的技术基础。

## 1. 新约束下的选型标准（权重重排）

| # | 标准 | 权重 | 为什么对"个人 + AI 开发"是这个权重 |
|---|------|:----:|-----------------------------------|
| 1 | **AI 可独立运行与验证** | **22** | AI 无法确认自己写的代码是否正确；能自动跑起来、截图、跑测试的栈，等于给 AI 装了眼睛 |
| 2 | AI 训练语料密度与生成质量 | 14 | 语料越厚，AI 一次写对的概率越高、幻觉越少 |
| 3 | 反馈闭环速度 | 14 | "改一行 → 看到结果"的秒数，直接乘以一个项目的迭代次数 |
| 4 | 纯文本工程（无 GUI 编辑器依赖） | 12 | AI 只能操作文本；二进制资源与场景文件会让 AI 的工作不可 diff、不可合并、不可回滚 |
| 5 | 内容与数据管线 | 12 | 本作是内容量驱动（24 张表 / ≈7,100 行），管线必须能被 AI 直接生成与校验 |
| 6 | 跨端发布覆盖 | 10 | 目标是移动端 + PC，能顺带覆盖 Web/小游戏就是净收益 |
| 7 | 表现力上限（2.5D 水墨 + 光照） | 8 | 重要，但权重低于"能否做出来" |
| 8 | 移动端性能与内存 | 6 | 重要，但本作是 2D 内容型，压力可控 |
| 9 | 商业化成熟度（支付/成就/防破解） | 2 | 可后置处理，且有规避路径 |

> 对比上一版引擎报告用的是"产品/性能"权重（双端 20 / 2.5D 18 / 数据 16 / 生态 14 …）。**同一份技术事实，两套权重会得出不同结论——这不是矛盾，而是目标函数变了。**

## 2. 四栈综合对比大表

> 打分为 1~5（5 = 最契合"个人 + AI 开发"）。

| 维度（权重） | **Phaser 3 + TS + Vite** | Unity 6.x LTS | Cocos Creator 3.8 | Godot 4.6 |
|--------------|:------------------------:|:-------------:|:-----------------:|:---------:|
| AI 可独立运行验证（22） | **5** — 无头 Chrome 可跑、可截图、vitest/Playwright 可自动化 | 2 — 需编辑器 GUI + 许可证；场景不可文本验证 | 2.5 — CLI 可构建，预览仍依赖编辑器 | 3 — 有 `--headless`，但 GDScript 语料少 |
| AI 语料与生成质量（14） | **5** — JS/TS 是语料量第一的语言 | 4.5 — C#/Unity API 语料厚 | 3.5 — 中文语料多，总量小 | 2.5 — GDScript 少 + 4.x API 变动大 |
| 反馈闭环速度（14） | **5** — Vite HMR 毫秒级，纯浏览器刷新 | 2 — 编译 + 域重载 + 编辑器启动 | 3 — 预览较快但仍需编辑器 | 3.5 |
| 纯文本工程（12） | **5** — 全文本，diff/回滚/合并友好 | 2 — `.unity`/`.prefab`/`.meta` 为编辑器产物 | 2.5 — `.scene`/`.prefab` 为 JSON，略好 | 3.5 — `.tscn`/`.tres` 是文本 |
| 内容与数据管线（12） | **5** — JSON/TS 表 + zod 校验 + vitest，AI 可直接跑 | 3.5 — 需自建导入器 + 编辑器扩展 | 4 — 国内表格工作流成熟 | 3 |
| 跨端覆盖（10） | **5** — 浏览器/PWA/Capacitor/Electron/小游戏全覆盖 | 4.5 — 移动/PC/主机强，Web 弱、小游戏需转换 | 4.5 — 移动 + 小游戏强，主机无 | 3.5 — 主机需第三方，小游戏无 |
| 表现力 2.5D 水墨（8） | 3 — 等距需自建；Light2D 基础；光照靠烘焙 + shader | **5** — Isometric Tilemap + URP 2D 光照开箱即用 | 3 — 2.5D 需自建 | 3.5 |
| 移动端性能/内存（6） | 2.5 — WebView/WebGL 上限低于原生 | **4.5** | 4.5 | 4 |
| 商业化成熟度（2） | 2.5 — Steam 需自建、IAP 需插件、代码可读 | **5** | 4 | 3.5 |
| **加权总分** | **4.64** | **3.23** | **3.28** | **3.22** |

**读表要点**

- Phaser 的领先**几乎全部来自前 6 项（权重 84%）**，即"AI 能不能干活"；它在第 7、8、9 项（权重 16%）是明显劣势。
- Unity 的优势**全部集中在后 3 项（16%）**——表现力、性能、商业化。**如果你的美术方案不依赖真 2.5D 光照、且移动端不是首发重点，这 16 分的优势就不成立。**

## 3. Phaser 栈的落地方案（具体到包与目录）

### 3.1 技术栈清单

| 层 | 选型 | 说明 |
|----|------|------|
| 语言 | **TypeScript 5.x（strict）** | 类型是 AI 写大项目不出错的护栏；也能让 AI 自己发现错误 |
| 引擎 | **Phaser 3.x 最新稳定版（锁定小版本）** | ⚠️ Phaser 4.0 已在官方仓库进入 4.0 阶段（有 v4.0.0 CHANGELOG），但**稳定度与插件生态待核实**；建议先锁 3.x，在 Gate 阶段单独实测 4 |
| 构建 | **Vite** | 冷启动与 HMR 极快；`vite build` 产出纯静态包，直接可托管 |
| 逻辑测试 | **Vitest** | 战斗内核、数值、存档迁移、配置表校验 |
| E2E / 视觉 | **Playwright**（或直接用本机 Chrome 无头） | 截图回归、UI 流程自动化 |
| PC 打包 | **Electron**（或 Tauri 2 体积更小） | Steam 需要 steamworks 集成；Electron 生态更成熟 |
| 移动打包 | **Capacitor 8.x** | iOS/Android 原生壳 + 插件（文件、IAP、安全区、状态栏） |
| 数据校验 | **zod**（或等价 schema 库） | 配置表 schema 即文档，校验失败直接报错 |
| 存档 | 纯 JSON + 校验字段 + 版本迁移函数 | 与引擎解耦，天然跨端互通 |

### 3.2 2.5D 等距水墨的具体实现路径（可行性论证）

**核心结论：本作需要的是"斜视角视觉"，不是"真 3D 等距引擎"。** 拆开看：

| 需求 | 实现方式 | 难度 |
|------|----------|------|
| 斜视角场景 | 标准等距投影数学 `screenX = (gx - gy) * (tileW/2)`，纯公式，AI 写得又快又对 | 低 |
| 深度排序 | 按 `(gx + gy)` 排序 + 分层容器（地面/建筑/角色/前景） | 低 |
| 九宫格站位 | **本质是 UI 层**，不需要真三维空间 | 低 |
| 水墨质感 | **美术资产问题，与引擎无关**（笔触、留白、宣纸纹理、色调） | 中（最大工作量在美术） |
| 光影氛围 | **优先"光照烘焙进贴图"**（美术侧画死在图里）+ Phaser **Light2D** 做少量动态点缀（灯、火把、技能光） | 中 |
| 天气/昼夜 | 全屏色调叠加 + 粒子 + 图层透明度，不用实时全局光 | 低 |
| 技能特效 | Phaser 粒子 + 后处理（Phaser 3.60+ 有 FX 管线）+ 序列帧 | 中 |

> **判断**：如果美术方案落到"**手绘背景 + 2D 精灵角色 + 烘焙光照 + 轻量氛围光**"，Phaser 与 Unity 的差距基本消失；如果非要"**角色走位时会被动态光源实时照亮、阴影随光源变化**"，那 Unity 的 URP 2D 明显更省事。

### 3.3 战斗与数值的可验证性（本作真正的核心）

GDD 5.4 明确要求：**预结算与表现分离、同种子同结果、单场战斗逻辑 < 50ms、可批量跑 100 场模拟**。这在 Web 栈里是**天然优势**：

```
纯函数战斗内核（不 import Phaser）
   src/core/battle/          ← 纯 TS，无渲染依赖
   src/core/formula/         ← 伤害/命中/暴击/连招/词条（GDD 3.1）
   src/core/progression/     ← 修为/境界/悟性门槛（GDD 3.3~3.4）
   src/data/*.json           ← 24 张配置表（GDD 4.7.2）
   tests/battle.spec.ts      ← 100 场自动模拟，输出 TTK/胜率/流派分布
   tests/tables.spec.ts      ← 引用完整性、概率和、数值边界、单调性
```

- **确定性要求**：核心逻辑用**整数/定点数**，避免 `float` 跨端差异（GDD 5.4 已列此风险）。
- **这些事情我可以自己跑完并把报告给你**——Unity 栈下同样的验证需要人打开编辑器点。

### 3.4 多端发布矩阵

| 目标平台 | 方式 | 可行性 | 备注 |
|----------|------|:------:|------|
| 浏览器（官网/Demo） | `vite build` 静态托管 | ✅ | 可直接做免费试玩 Demo，拉愿望单 |
| PWA | manifest + Service Worker | ✅ | 可安装到桌面，离线可玩 |
| iOS / Android | Capacitor 8 | ✅ | 需插件：IAP、文件系统、安全区；**WebView 性能是主要风险** |
| Windows / macOS / Linux | Electron 或 Tauri 2 | ✅ | Tauri 体积小（用系统 WebView），Electron 生态成熟 |
| **Steam** | Electron + `steamworks.js` | ✅⚠️ | 成就 / 云存档 / Overlay 可接；**必须实机验证**，Valve 不禁止 HTML5/Electron 游戏 |
| 微信 / 抖音小游戏 | H5 原生 + 适配层 | ✅⚠️ | **这是 Web 栈对 Unity 的独有优势**（原生主场）；但受代码包大小限制 |
| 主机 | — | ❌ | Web 栈无主机路径；主机需求出现即需换栈 |

### 3.5 包体与资源策略（Web 栈是降维优势）

| 项 | 目标 | 说明 |
|----|------|------|
| Web/桌面首包 | JS + 核心图集 ≤ 30~50MB | 远小于原生方案的 300MB |
| 移动端（Capacitor） | 首包 ≤ 100MB，其余资源远程下载 | 需网络策略与断点续传 |
| 图集 | 单张 ≤ 2048²，按区域/系统分包 | 控制显存与加载 |
| 小游戏 | 主包 ≤ 4MB 级限制 ⚠️（需核实当前阈值），其余走 CDN 分包 + 域名白名单 | 小游戏只适合做"轻量版/入口"，不适合承载全量 2.5GB 内容 |
| 配置表 | JSON + gzip（或二进制） | 全量加载目标 < 200ms |

### 3.6 存档与跨端

统一使用**引擎无关的 JSON**（zod 校验 + 版本迁移），存储层按平台适配：

| 平台 | 存储 | 备注 |
|------|------|------|
| 浏览器 | IndexedDB（+ 导出/导入存档码） | 容量足够 |
| 小游戏 | 小游戏本地缓存 API | 需适配层 |
| Capacitor | Filesystem 插件 | 沙盒目录 |
| Electron | 用户目录文件 + Steam Cloud | steamworks.js 云存档 |

**收益**：GDD 5.2 的 Gate「手机 ↔ PC 存档可互转」在 Web 栈里几乎自动满足。

## 4. 与 Unity 方案的逐项对决

| 分歧点 | Phaser + TS | Unity 6.x LTS | 本项目谁更优 |
|--------|-------------|---------------|--------------|

| 内容量产速度 | 配置表 + 校验全自动，AI 直接生成 | 需先自建导入器与编辑器扩展 | **Phaser** |
| 引擎学习成本（对人） | 低（HTML/JS 门槛最低） | 中（编辑器 + C# + 生命周期） | **Phaser** |
| 引擎学习成本（对 AI） | 低（语料最厚） | 低（语料也厚，但验证难） | 平 |
| 跨端覆盖 | Web + 移动 + PC + 小游戏 | 移动 + PC + 主机 | 平（看目标） |
| 商业化与 IAP | 需插件、国内渠道 SDK 摩擦大 | 成熟 | Unity |
| 反破解/资产保护 | JS 可读、易被扒 | 可 IL2CPP 加固 | Unity |
| 出包体积 | 小 | 大 | **Phaser** |
| 崩溃/兼容性排查 | 浏览器报错文本化、可粘贴 | 需真机日志链路 | **Phaser** |
| 长期维护 | 依赖 npm 生态活跃度 | 依赖 Unity 政策 | 平（各有风险） |

## 5. 必须正视的五个真风险（不粉饰）

### R1 · 移动端 WebView 性能与内存（最大技术风险）
- **现实**：iOS WKWebView 与 Android WebView 的 WebGL 上限低于原生；iOS 对 WebView 内存有硬约束（[[Gamemaker 官方文档：iOS 浏览器游戏资源限制](https://test.gamemaker.io/zh-CN/help/articles/html5-resource-limits-for-browser-games-on-ios)]①），大图集容易触发被杀。
- **对策**：① 图集 ≤ 2048² 且按需卸载；② 禁止同时驻留多区域资源；③ 战斗表现用预结算 + 轻量动画；④ 首包只放序章；⑤ **在 Gate 阶段就用中低端 Android 真机实测**（这是我无法替你做的验证）。
- **不通过就切 Unity**——这是硬门槛。

### R2 · 反破解与资产保护
- **现实**：打包后的 JS 可读、资源可被扒。单机离线游戏尤其难防。
- **对策**：① 代码压缩 + 混淆（如 terser + javascript-obfuscator）；② 关键数据不落本地明文；③ **接受一定盗版率**——买断制单机游戏的盗版损失通常不致命，销量主要靠口碑与宣发。
- **判断**：对本作**可接受**，但要提前知情。

### R3 · 国内安卓渠道与 IAP 的集成摩擦（最容易被低估）
- **现实**：Apple 要求数字内容走 StoreKit；国内安卓渠道（华为/小米/OPPO/vivo/应用宝）各有原生 SDK，**WebView 包装下逐个接渠道 SDK 的成本很高**。
- **对策（推荐）**：① **PC/Steam 买断制先行**（无需版号、无需渠道 SDK）；② 移动端先做**海外 iOS/Google Play**（IAP 只需一套插件）；③ **国内安卓渠道延后或不做**，国内只保留 iOS + 官网/自有渠道，或直接以"付费下载 App"形式（仍需版号）。

### R4 · AI 幻觉与版本漂移
- **现实**：Phaser 3 → 4 是重大变更（⚠️ 稳定度待核实）；AI 可能混用两版 API。
- **对策**：① **锁定 Phaser 3.x 具体版本并写进 `package.json`**；② 把官方文档要点固化进仓库 `docs/engine-notes.md` 作为 AI 的上下文；③ 用 TypeScript 类型 + 单元测试兜住 API 误用（类型不匹配会直接编译失败，AI 能自己发现）。

### R5 · 美术产能（**比引擎选型更致命，且引擎无关**）
- **现实**：2.5D 水墨资产（等距地块、八向角色、动画、立绘、UI）是个人开发的真正瓶颈。GDD 4.8 估算美术 800 人日，**AI 对"代码/文案/表格"能压缩 3~5 倍，对"美术资产"只能压缩 1.2~1.5 倍**。
- **对策（强烈建议）**：① **把表现形态从"真 2.5D 等距"降级为"手绘背景 + 斜视角精灵"**——背景一张画好，角色只需单朝向或左右两向，工作量下降一个数量级；② 立绘用 AI 生成 + 人工统一风格；③ 场景复用模块化；④ UI 走组件库。
- **这条决定了项目能不能做完，比选引擎重要得多。**

## 6. 成本与周期对比（个人 + AI 口径）

**估算方法**（不硬给数字，给可复算的模型）：

```
周期 = Σ(工作量 × AI 压缩系数) ÷ 有效人日/月
AI 压缩系数：文本型工作（代码/配置/文案/测试）≈ 0.2~0.33（即 3~5× 提速）
             资产型工作（美术/音频）≈ 0.67~0.83（即 1.2~1.5× 提速）
             引擎学习与调试 ≈ 0.3（Web 栈） / 0.6（Unity 栈，因为验证依赖人）
```

| 项 | Web 栈（Phaser+TS） | Unity 栈 | 差异来源 |
|----|---------------------|----------|----------|
| 引擎学习曲线 | 低（HTML/JS 基础即可） | 中（编辑器 + 生命周期 + C#） | AI 语料 + 验证闭环 |
| 系统代码（战斗/养成/门派） | 快 | 中 | TS 纯逻辑 + vitest 可自测 |
| 配置表与校验工具链 | 快（node 脚本 + zod） | 慢（需 Unity 编辑器扩展或外部工具） | 工具链是否纯文本 |
| 2.5D 渲染管线 | 慢（自建等距 + 光照烘焙方案） | 快（原生） | **Unity 追回一局** |
| 移动端性能调优 | 慢且有天花板 | 中 | **Unity 追回一局** |
| 双端出包与 CI | 快（静态包 + 壳） | 中 | Web 产物天然跨平台 |
| 美术资产 | 800 人日（**两栈相同，且是主要瓶颈**） | 800 人日 | 与引擎无关 |
| **瓶颈结论** | **瓶颈 = 美术产能** | **瓶颈 = 美术产能 + 引擎验证人力** | Web 栈少一个瓶颈 |

**关键推论**：Web 栈把项目的瓶颈从"两个"（美术 + 引擎验证）收敛到"一个"（美术）。对个人开发，**瓶颈数量比单点效率更重要**。

## 7. 决策建议与 2 周 Gate

### 7.1 建议

| 项 | 结论 |
|----|------|
| **首选** | **TypeScript + Phaser 3 + Vite**（PC/Steam 用 Electron，移动用 Capacitor） |
| 备选 | **Unity 6.x LTS**（触发条件见 7.3） |
| 第二备选 | Cocos Creator 3.8（若首发重心转小游戏/鸿蒙且团队有 Cocos 经验） |
| 前置决策 | **把美术表现形态定下来**（真 2.5D 等距 vs 手绘背景 + 斜视角精灵）——这比选引擎更早、更重要 |

### 7.2 2 周 Gate（可量化，我无法替你验的必须你真机验证）

| # | 验证项 | 通过标准 | 谁来验 |
|---|--------|----------|--------|
| 1 | 水墨质感 | 用 Phaser 渲染一张手绘背景 + 斜视角角色 + 烘焙光照，**截图与美术参考稿主观对比通过** | 我出截图，你判断 |
| 2 | 中低端 Android | 真机 ≥ 30FPS、内存 < 800MB（含 1 个场景 + 1 场 4v4 战斗） | **你** |
| 3 | iOS | 真机不崩溃、能正常存档读档 | **你** |
| 4 | Steam 出包 | Electron 出 Windows 包，**成就 + 云存档 + Overlay 至少一项打通** | 你我配合 |
| 5 | 战斗内核 | 100 场自动模拟跑通，TTK 与 GDD 3.1.5 目标偏差 ≤ 30% | **我** |
| 6 | 配置表管线 | 24 张表跑通 schema 校验 + 边界校验，AI 新增一条奇遇 ≤ 10 分钟生效 | **我** |
| 7 | 开发闭环 | `pnpm dev` 起服务 → 改代码 → 浏览器看到变化 < 3 秒 | 我（需你先装依赖） |
| 8 | 包体 | Web 首包 ≤ 50MB；Capacitor 首包 ≤ 100MB | 我 |

**判定规则**：1、5、6、7、8 由我出证据；**2、3、4 任一失败 → 切 Unity**；1 不通过 → 先改美术方案，再决定引擎。

### 7.3 切换到 Unity 的触发条件（任一命中即认真评估切换）

1. 移动端 WebView 真机无法稳定 30FPS，或内存超标无法收敛。
2. 美术方案确定必须**真 2.5D 等距 + 实时动态光照**（角色被动态光实时照亮）。
3. 需要**主机版**（PS/Xbox/Switch）作为目标平台。
4. 需要在国内安卓多渠道做内购发行（渠道原生 SDK 集成成本过高）。
5. Steam 上架遇到 Electron 无法解决的实机问题（如 Overlay/成就稳定性）。

> **切换成本可控的关键**：GDD 3（数值框架）、GDD 4（内容与配置表）以及与引擎无关的存档 JSON **在两个栈里完全通用**。这也是为什么可以"先用 Web 栈验证系统与内容，再决定是否迁移"。
