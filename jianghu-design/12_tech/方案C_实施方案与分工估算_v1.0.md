## 3. 我需要的 token 估算

**估算方法**（不是猜，按可复算的模型）：

**公式**：token ≈ Σ（文件行数 × 15）×（1 + 迭代系数）×（1 + 跨会话重读冗余）。

其中：15 = 每行 TS（含中文注释）约 15 tokens；迭代系数 = 1.5~2.5（写完后调试、返工、按你反馈调整）；重读冗余 = 0.25（每次新会话我要重读相关文件）。

| 阶段 | 交付物 | 代码/数据量 | token 区间 |
|:----:|--------|:-----------:|:----------:|
| **P0** | 规范 + 骨架 + schema | ~500 行 | **3~4 万** |
| **P1** | 最小可跑：`Rig` + `MotionPlayer` + `SkinRegistry` + 1 个特效 + 1 角色 3 动作 | ~1,200 行 | **15~21 万** |
| **P2** | 56 clip 草稿生成器 + `gongfa_visual`（87 行）+ 16 特效模板 | ~900 行 + 数据 | **10~15 万** |
| **P3** | **浏览器内时间轴编辑器** | ~1,200 行 | **25~40 万** |
| **P4** | `BattleView` 编排 + `HitStop` + 连招叠加 + 九宫格投影 | ~900 行 | **18~28 万** |
| **P5** | 脚本 + 单元测试 + 性能降级 + 集成调试打磨 | ~1,000 行 | **20~32 万** |
| | **合计（完整系统）** | **~5,700 行** | **≈ 91~140 万** |

### 分档结论

| 档位 | 覆盖范围 | token | 你何时需要 |
|------|----------|:-----:|------------|
| **A · 最小闭环** | P0 + P1（1 角色 3 动作能打一场） | **18~25 万** | **现在就该做**（2 周内看到画面） |
| **B · 可用动作库** | A + P2 + P4（56 clip 草稿 + 87 映射 + 战斗编排） | **43~64 万** | 垂直切片阶段 |
| **C · 完整系统** | B + P3 编辑器 + P5 打磨 | **91~140 万** | 量产前 |

**建议节奏**：**A（现在）→ B（验证手感后）→ C（确认要量产时）**。不要一上来做 C——编辑器的价值只有在"你真的要调 56 个动作"时才兑现。

> ⚠️ **不确定性说明**：token 估算最大变量是**迭代轮数**（尤其编辑器：交互细节多，可能来回 5~10 轮）。如果需求反复，上表可能 ×1.5。**控制方法：每阶段先冻结验收标准，再让我动手。**

## 6. 动作库怎么设计（核心方法论）

### 6.1 先定"动作原型"，不做"逐功法动画"

**公式**：动作数量 = 动作组数量 × 原型数量（← 与角色数、功法数都无关）= (6 武器组 + 内功组 + 身法组) × 各自动作原型。

| 动作组 | 原型（8 个） | 数量 |
|--------|--------------|:----:|
| 刀 / 剑 / 拳掌 / 暗器 / 奇门 / 枪 | `idle` · `ready` · `atk_a` · `atk_b` · `cast` · `hit` · `dodge` · `down` | 6×8 = 48 |
| 内功 | `idle` · `meditate` · `cast` · `aura` | 4 |
| 身法 | `dash` · `leap` · `vanish` · `land` | 4 |
| **合计** | | **56** |

### 6.2 命名与数据结构

**命名规则**：`{group}_{archetype}[_{variant}]`

| 命名示例 | 含义 |
|----------|------|
| `dao_atk_a` | 刀·快招 |
| `dao_atk_b` | 刀·重击 |
| `qiang_sweep` | 枪·横扫（打整排） |
| `neigong_meditate` | 内功·打坐运气 |
| `shenfa_dash` | 身法·疾冲 |

**Clip 数据格式（JSON）**

顶层字段如下：

| 字段 | 类型 | 说明 | 示例值 |
|------|------|------|--------|
| `id` | string | clip 标识 | `dao_atk_a` |
| `group` | string | 动作组 | `dao` |
| `duration` | number（ms） | 时长 | `520` |
| `loop` | boolean | 是否循环 | `false` |
| `priority` | number | 打断优先级：受击(5) > 攻击(2) > 待机(0) | `2` |
| `anchors` | object | 挂点：特效只认挂点，不认动作名 | 见下 |
| `events` | array | 时间点事件 | 见下 |
| `tracks` | array | 各 slot 的关键帧轨 | 见下 |

**anchors（挂点）**

| 挂点 | 值 |
|------|----|
| `weaponTip` | `[ { "t": 0.25, "x": 42, "y": -18, "angle": -35 } ]` |
| `hitPoint` | `[ { "t": 0.35, "x": 55, "y": -10 } ]` |

**events（事件）**

| t | type | id | 说明 |
|:--:|------|----|------|
| 0.00 | `sfx` | `swing_light` | 播放音效 |
| 0.35 | `hit` | — | 命中判定点（表现用） |
| 0.50 | `vfxStop` | — | 特效停止 |

**tracks（关键帧轨）**

| slot | keys |
|------|------|
| `torso` | `[{t:0,rot:0,x:0,y:0,ease:"sineOut"}, {t:0.3,rot:-8,x:4,y:-2}, {t:1,rot:0,x:0,y:0}]` |
| `upperArmR` | `[ /* ... */ ]` |
| `weapon` | `[ /* ... */ ]` |

**设计规则（写进规范，避免动作库失控）**

| 规则 | 值 | 理由 |
|------|:--:|------|
| 每部件关键帧数 | **8~14 个** | 再多收益递减，且手调成本高 |
| 单 clip 时长 | 300~700 ms（`cast` 可到 1200） | 配合自动战斗节奏 |
| 必填挂点 | 每个攻击 clip 必须有 `weaponTip` 或 `palm`/`throwPoint` | 特效依赖 |
| 缓动 | 只用 4 种：`linear` / `sineOut` / `quadIn` / `backOut` | 统一手感，减少选择成本 |
| 循环动作 | `idle` 必须可循环且首尾帧一致 | 避免跳帧 |
| 过渡 | 统一 100 ms 交叉淡入 | 不用逐对配置过渡 |
| 变体优先 | 新功法**优先改参数**，不新增 clip | 这是省 19 倍的关键 |

### 6.3 动作库的三层结构

| 层 | 动作 | 说明 |
|----|------|------|
| 基础层 | `idle` / `ready` | 每个动作组必须有，12 角色共用 |
| 动作层 | `atk_a` / `atk_b` / `cast` / `sweep` | 战斗中 95% 时间在播这一层 |
| 状态层 | `hit` / `dodge` / `down` / `dash` / `leap` | 被打断时覆盖播放 |

### 6.4 动作 → 功法 的映射（87 门功法只写 87 行）

`gongfa_visual.ts` 每行只描述**差异**，示例三条如下：

| id | group | motion | vfx | timingScale | hitStopMs | shake | sfx | targets |
|----|-------|--------|-----|:-----------:|:---------:|:-----:|-----|---------|
| `GF_kuangfeng_dao` | `dao` | `cast` | `slash_arc` | 1.15 | 40 | 1 | `slash_1` | `single` |
| `GF_duanyue_dao` | `dao` | `atk_b` | `slash_heavy` | 0.85 | 90 | 2 | `slash_heavy` | `column` |
| `GF_badao` | `dao` | `atk_b` | `slash_heavy` | 0.75 | 120 | 2 | `slash_heavy` | `all` |

> **霸刀与断岳刀法共用 `slash_heavy`**，只改尺寸/颜色/时序/停顿/震屏/范围。**这就是不加动画也能做出"不同的功法"。**

### 6.5 品质 → 表现（零成本差异化）

| 品质 | 主色 | 表现叠加 |
|------|------|----------|
| 凡品 | 灰白 | 基础粒子 |
| 良品 | 青碧 | + 轻拖尾 |
| 上品 | 靛蓝 | + 拖尾 + 光晕 |
| 极品 | 暗金 | + 拖尾 + 光晕 + 残影 |
| 绝世 | 赤金 | + 全屏闪 + 墨迹扩散 + 镜头轻推 |

**连招叠加**：二连（+30%）加一层拖尾，三连（+60%）叠墨迹爆点 + 震屏加强 —— **让数值加成"看得见"**。

### 7.2 作画硬规则

| # | 规则 | 原因 |
|:-:|------|------|
| 1 | **统一朝向：面向右 3/4 斜视角** | 等距视角惯例；朝左用程序水平翻转，**省一半贴图** |
| 2 | **枢轴必须在关节旋转中心** | 枢轴错位 → 动作一摆就穿模，且无法修 |
| 3 | 部件间**重叠 8~12 px** | 旋转时露缝 |
| 4 | 边缘加 **4~6 px 半透明墨迹虚边** | 强化水墨感 + 遮缝（一举两得） |
| 5 | 透明背景 PNG，**不裁边**（保留画布尺寸） | 保证枢轴一致 |
| 6 | 命名严格 = slot 名（`torso.png` / `upperArmL.png`） | `skin.json` 自动生成 |
| 7 | 每角色一张调色板 `palette.json` | 精英怪/变体复用同一套图，只换色 |
| 8 | 立绘与战斗部件**分开两组资产** | 战斗用小尺寸，剧情用大立绘 |
| 9 | 角色剪影先过审再细化 | 剪影决定辨识度，改剪影比改细节便宜 10 倍 |

### 7.3 武器贴图按「类型 × 品质」共享（又省一大块）

| 路径 | 内容 |
|------|------|
| `weapons/` | 武器贴图根目录 |
| `weapons/dao/` | `dao_fan.png` `dao_li.png` `dao_bao.png` `dao_shen.png` `dao_chuan.png` |
| `weapons/jian/` | `jian_fan.png ...` |
| `weapons/quan/` | （拳套/护手） |
| `weapons/anqi/` | `anqi_*.png` |
| `weapons/qimen/` | `qimen_*.png` |
| `weapons/qiang/` | `qiang_*.png` |

- **6 类型 × 5 品质 = 30 张武器图，全角色共用。**
- 玩家认知自然（"这是一把宝器剑"），且**外观付费的切入点**：角色专属武器皮肤 / 时装 → 对应 GDD 0.5 的"外观付费，不卖数值"。
- 角色专属武器只在**传世品质 + 剧情关键**时才单独画。

## 8. 怎么接进你的游戏项目

### 8.1 与战斗系统的对接（关键：表现层不参与计算）

**逻辑层·纯 TS，可 vitest**

- 战斗预结算（GDD 5.4 强制）→ 产出 `BattleEvent[]`。
- `BattleEvent` 字段如下：

| 字段 | 说明 |
|------|------|
| `t` | 时间点 |
| `type` | `'attack' \| 'hit' \| 'heal' \| 'buff' \| 'die'` |
| `actorId` | 施放者 |
| `targetIds` | 目标 |
| `gongfaId` | 功法 |
| `comboLevel` | 连招层级 |
| `damage` | 伤害 |
| `crit` | 是否暴击 |

**表现层·Phaser**

`BattleView` 读事件流后的处理步骤：

1. 逐条调用 `CharacterAnimator.play(gongfaVisual[gongfaId])`。
2. `VfxLayer` 在挂点上生成特效。
3. `HitStop` / 震屏 / 飘字。
4. 支持 1×/2×/4×/跳过（跳过 = 直接把状态设到结果）。

**收益**：① 逻辑可单测、可批量模拟（GDD 3.10 要求）；② 低端机表现降级不影响战斗结果；③ 同种子同结果（GDD 5.4 要求）天然成立。

### 8.2 与九宫格布阵的对接

1. 格位(0~8) → 等距屏幕坐标：`screenX = originX + (col - row) * TILE_W/2`；`screenY = originY + (col + row) * TILE_H/2 - heightOffset`。
2. 渲染层级 = `(col + row)` 升序 → 后排先画、前排压住。
3. 出手顺序由逻辑层决定，表现层只按事件流的 `t` 排序播放。

### 8.3 与功法/品质/境界/连招的对接（已有系统，只需挂接）

| 已有系统 | 挂接点 | 改动 |
|----------|--------|:----:|
| 功法系统（87 门） | `gongfa_visual.ts` 按 id 关联 | **新增 87 行** |
| 品质体系 | 特效颜色 + 光效强度 | 查表 |
| 境界体系（十境） | 高阶境界加"气劲光环"（`aura` 挂点） | 查表 |
| 连招系统（+30%/+60%） | `comboLevel` → 特效叠加层 | 新增参数 |
| 状态（眩晕/击退/封穴） | 头顶图标 + 位移表现 | 新增 3 个小组件 |
| 属性系统 | 攻速 → `timeScale`；身法 → 位移速度 | 只读 |
| 门派/弟子 | 弟子复用同一骨架 + 调色板 | **零新增贴图** |

### 8.4 与内容管线的对接（这是长线成本的关键）

| 新增内容 | 需要做的事 | 成本 |
|----------|-----------|:----:|
| 新增 1 门功法 | `gongfa_visual.ts` 加 **1 行** | **10 分钟** |
| 新增 1 个伙伴 | 加 **1 套部件贴图** + 自动生成 skin | **1~2 人日** |
| 新增 1 个弟子/敌人 | 复用现有皮肤 + 换调色板 | **10 分钟** |
| 新增 1 种武器类型 | 加 **1 组动作（8 clip）** | **2~3 人日** |
| 新增 1 个特效 | 加 **1 个模板** | **0.5~1 人日** |

> 这就是方案 C 的复利：**游戏上线后每加一个角色/功法，成本几乎不变**——GDD 5.8 的 DLC 长线计划才成立。

## 9. 方案怎么设计最优（8 条优化建议）

| # | 优化 | 收益 |
|:-:|------|------|
| 1 | **先做 P1 最小闭环再决定投全套** | 用 18~25 万 token + 你 3~5 人日，2 周内看到能动起来的战斗；不行就止损 |
| 2 | **动作数据由我程序生成草稿，你只做微调** | 调动作时间省 **50%+**（从白纸摆关键帧是最慢的方式） |
| 3 | **武器按「类型 × 品质」共享（30 张）** | 省掉 12 角色 × 6 类型的武器贴图（≈72 张 → 30 张） |
| 4 | **编辑器优先于内容**（P3 放在量产前） | 否则每次改动作都要我介入 → 我成为瓶颈 |
| 5 | **镜头 + 命中停顿优先于动作精细度** | 自动战斗下，观感提升性价比最高的是 hitstop/震屏/飘字，不是多 4 帧 |
| 6 | **大招用「立绘切入 + 全屏特效」** | 回避为每个大招做复杂动作，且强化"爆技能"爽点 |
| 7 | **贴图先行过剪影评审** | 剪影不对，画得再细也认不出角色；改剪影便宜 10 倍 |
| 8 | **表现分级降级开关** | 保证低端机（GDD 5.4：中低端 Android ≥30FPS / 内存 <800MB） |

### 9.1 一个更激进的省法（可选）

**战斗用"Q 版剪纸小人"（高约 96~120 px），剧情/大招用"半身立绘"（400~600 px）。**

- 战斗小人部件少（可简化为 8 个部件）、无需精细，**贴图量再降 40%**
- 立绘走 AI 生成 + 人工统一，成本低
- 观感上反而更像"江湖画册"，与水墨风格一致
